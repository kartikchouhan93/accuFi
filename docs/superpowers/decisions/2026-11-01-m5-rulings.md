# AccuFi M5 — decisions taken during implementation

Every ruling made while executing `docs/superpowers/plans/2026-11-01-accufi-m5-budgets.md` (budgets), numbered R1 onward in
the order they were made. Each records what was ruled, why, and what it costs if it turns out to be wrong. The design is
`docs/superpowers/specs/2026-11-01-accufi-m5-budgets-design.md`; it was amended in execution by R1 and R3. R4 is a wording
fix made after the first review, and R5 to R10 were made in the fix wave that followed the whole-branch review. What review
found and the wave left alone, on purpose, is under "Known and parked".

---

### R1: A budget warning is judged on the state after the write, and on nothing else

What was ruled: `BUDGET_OVER` is carried when a covering budget ends over, and `BUDGET_NEAR` when it ends near (80% or more,
not over), for any write whose destination is a ledger the budget counts and whose date is in a month the budget covers and
not after today. The design's "newly near" and "newly over" (a warning only when this write is what crossed the line) are
dropped, and so is the plan's "an edit that lowers the amount carries none". A refund (the destination is not an expense
ledger) and a future-dated entry carry no budget warning.
Why: the warning is built from the stored row after the write (`warningsFor` has no previous row), and handing it the
previous amount would have widened every write path (record, split, edit, restore, the investment legs). The spec says only
that exceeding a budget warns, and the existing warning channel already speaks about the state a write left.
Cost if wrong: while a budget stays over or near, every further entry repeats the notice, and so does an edit that lowers the
spend but still ends over. Fixing it means threading the previous amount through the edit paths.

### R2: The warning step's test list is amended to match R1

What was ruled: the cases "a lowering edit carries none" and "from 70% to 85% is a crossing" are dropped from the tests of
the warnings. What is kept: 85% ends NEAR; 105% ends OVER with the exact over-by; a second entry while already over still
carries OVER; below 80% carries none; a refund carries none; a future-dated entry carries none; a backdated entry is judged
against its own month; a child's entry warns for both the child's and the parent's budget; a failure to judge is swallowed
and logged with the `[budgets]` prefix (a budget is never a reason for a write to fail).
Cost if wrong: none beyond R1; the dropped cases cannot be written until the previous amount is threaded through.

### R3: The sentence under "Applies from" is neutral: "Changes the amount from <month>; earlier months keep the old amount."

What was ruled: the plan's wording for a split ("Raises it from <month>...") was a defect, because the sentence also shows
beside a lowered amount, so the plan's string is replaced. The live sentence has the same signature as before
(`describeRevision(startMonth, appliesFrom, endMonth)`) and does not take the amounts: what is typed in the field can be empty
or not a number halfway through an edit. The other two sentences stand: "Corrects the amount for every month of this budget."
for a revision from the start month or earlier, and "This budget ended in <month>. Pick a month it applies to." for a month
after the end. The message shown after saving was already neutral ("Changed the ... budget to ... from <month>.").
Why: the spec says only that a revision says in words what will happen; the design's example text is illustrative.
Cost if wrong: nothing the user sees is lost. "Raises" and "Lowers" would need the amounts passed in and guarded against
invalid text.

### R4: A budget warning names its month unless it is the current one

What was ruled: when the entry's month is the current month (the user's today), the sentences stay "<ledger> is over budget by
<₹X> this month." and "<ledger> is at <n>% of its budget this month."; for any other month, "this month" is replaced by the
label the budgets screen uses, "in Apr 2026". An entry backdated into last month that takes last month over therefore says so
about last month, and two over months for one ledger give two sentences that differ.
Why: "this month" was false for a backdated entry, and the sentences for two months were identical.
Cost if wrong: one expression in `budgetWarningsForRows`.

### R5: A budget that starts after the current month is listed under "Upcoming", and saving one lands on the current month

What was ruled: `BudgetsScreen` carries `upcoming`, one entry per budget span whose start month is after the current month
(ledger, cap as paise text, start, end or none, rollover, archived), earliest start first, then ledger name. The screen
shows an "Upcoming" section for it, in the state where no budget has started (below the explanation) and below the cards
otherwise (also below "No budget covers this month"), and nothing when the list is empty. Each entry has the ledger's name, the
cap, "Starts <month>", an Edit link to the budget's edit page and a Delete behind the same confirm as a card, with the ledger
name as the screen-reader suffix. `upcomingStart` is gone: "the first start" the not-started heading names is the first
entry of `upcoming`, so there is one source. After a save, `landingMonth` is the current month for a budget that starts later
(it was the budget's start month, which the screen clamped to the current one and so showed no card); a budget that ended
before this month still lands on its own first month.
Why: a budget made for a later month had no card, so it could not be edited or deleted, a second create for the same months was
refused as an overlap with nothing to revise, and a ledger it used could not be deleted.
Cost if wrong: one extra read-only list on the screen. If the list is judged too prominent it can be moved or collapsed
without touching the service.

### R6: An edit opens within the budget's end month, and never offers a month after it

What was ruled: "Applies from" lists the budget's start month through the earlier of the current month and the budget's end
month, and opens on that same earlier month (it opened on the current month, which for a budget that ended is past its end and
put the refusal sentence on screen). Every span before a split is an ended budget, so this is the Edit of every earlier span.
The server's own refusal for a month after the end stays, with its wording corrected to "This budget ended in <Mon YYYY>. Pick
a month it applies to." (it read "<month> to <month>").
Why: the form should never open on a state it will refuse.
Cost if wrong: a person cannot pick a month after the end in the select, which the server would have refused anyway.

### R7: Saving the amount a budget already has writes nothing

What was ruled: `reviseBudget` validates as before (an unusable month is still refused), then, when the amount equals the stored
one, writes nothing and answers with the revised span as it is: one view, no new span, no change to the end, and no change to
the row's timestamp. It holds from any month, including the start month (an in-place write of the same figure only moved a
timestamp). The form says "Nothing changed." (and goes to the budgets screen with that message) instead of "Corrected ... for
every month".
Why: a split with an unchanged amount adds a span that says nothing new and makes the history longer for no reason.
Cost if wrong: a person who meant to save the same amount from a month to mark it gets no span; nothing in the figures differs.

### R8: Saving one section of the edit form while the other holds a change says so, and stays

What was ruled: the Amount and Settings sections save on their own. When one is saved while the other holds a value that
differs from what is stored, the form stays on the edit page, shows the saved message plus "Your change to the settings was not
saved." (or "...to the amount was not saved."), and leaves the other section filled in. When nothing differs it behaves as
before (goes to the budgets screen with its message). "Differs" is decided by pure helpers in `budget-fields.ts`: the amount
is compared as money (12345 is 12,345.00; a blank or unusable amount differs), the month the amount applies from does not
count, and the end month and the rollover count for Settings. After a save that stays, the form works on the budget the server
answered with: a split continues on the new span, so a following save goes to the live budget and not to the ended one.
Why: otherwise a change typed in the other section was dropped without a word behind a redirect.
Cost if wrong: after a split the address bar still names the earlier span (a reload shows that span); the message says what
happened, and Cancel leads back to the screen.

### R9: The delete confirm says what stays, and a one-month span reads as that month

What was ruled: the card's confirm reads "This removes the budget for <span>. Months before <the card's start month> keep their
earlier budget. Your transactions are not touched." The second sentence is always there, including for a budget that was never
split (then it is true of nothing). A span of a single month is labelled "Oct 2026", not "Oct 2026 to Oct 2026". The card's
"Used" link is announced with the month the card is for ("spending in Oct 2026"), not "this month".
Why: "and its history" was false after a split, and the fix was worded to be true whether or not there is an earlier span.
Cost if wrong: a never-split budget carries a sentence about earlier months that do not exist.

### R10: A write pays for budget warnings only when there are budgets

What was ruled: a user with no budgets costs a write one read of their budgets (no ledger listing and no spending query); the
caller's `today` is passed in, so a write works it out once; and the budget judgement runs beside the balance read, with the
warnings in the same order (OVERDRAWN, OVER_CREDIT_LIMIT, FUTURE_DATED, BUDGET_OVER, BUDGET_NEAR). A replayed or restored split
is judged as the whole group, exactly as the original call was, so the same warnings come back on every leg.
Why: every write used to run three reads for a feature most users have not switched on, and a replay did not answer what the
original answered.
Cost if wrong: none for the figures; the budget read now happens in parallel with the balance read, so a slow balance read hides
it rather than adding to it.

## Known and parked

Found in review and left alone on purpose, so a later reader does not mistake them for oversights. None of it puts money or
another user's data at risk. What the fix wave took (the upcoming list, the ended-budget form, the unchanged amount, the
other-section edits, the split replay, the cost per write and the test hazards) is no longer listed. Grouped by where it is.

**Domain (`src/domain/budgets.ts`)**
- Some `spansOverlap` test lines are long and the imports in `calendar-date.test.ts` are out of order; `evaluateMonths` assumes spans start on the first of a month, so services must normalise with `monthOf` (they do) and the function does not reject overlapping spans.

**Schema and repository**
- The RESTRICT foreign-key test asserts only `rejects.toThrow()` (assert the foreign-key error code, keep the ledger case, since the `user.delete` case is blocked by the nodes anyway); `amountPaise: 1n` is not asserted accepted; the accepted-cases test does not assert the stored values; one schema header comment line is long.
- The repository's blocking test waits 300 ms and then asserts the second transaction has not locked: a lock that took longer than that to be refused would pass it falsely, so it can only produce false passes, never false failures (its held transaction is now always released).
- `updateBudget` and `deleteBudget` isolation cases have no own-row positive control inside the isolation file; the ordering test expects JavaScript `localeCompare` on ids where the database collates; `insertBudget` without a unit of work checks and then creates in two statements (the service always passes one).

**Operations (service, actions and form loader)**
- The "two creates of different overlapping spans" race test passes even without the ledger lock (it is timing-dependent: make it deterministic or rename it); there is no create test for an amount of zero or less (the violation names only `amount`); the "different months" revise race assertion is loose.
- The `expectNoBigint` check in the action tests uses `JSON.stringify`, so a `Date` slips through silently (walk the value recursively); the foreign-ledger create and foreign update tests do not assert that nothing is revalidated on a refusal; `loadBudgetForm` returns `budget: null` if a budget's ledger lookup ever missed, which the foreign key makes unreachable, so the contract should be stated.

**Evaluation (`src/server/services/budget-report.ts`)**
- The seven-day projection assertion only checks "not null" (assert 841429 paise and `overAtPace`); no test says that a past selected month's `drillHref` ends on that month's last day; the 1 January and 31 December test uses only the default timezone; there is an unreachable `?? ""` fallback; `loadBudgetAttention` builds whole cards only to count statuses.

**Warnings and node delete**
- The node-delete check for a budget is not atomic (as for recurring rules); there is no test for a month after a budget's end.
- Posting from the recurring inbox never shows budget warnings (OVERDRAWN is not shown there either), so an occurrence posted from the inbox that takes a budget over says nothing.
- There is no "back under budget" message after a delete or an edit that lowers the spend: a warning speaks of the state a write left (R1), and nothing speaks when a write leaves a budget fine.

**Screen (`/budgets`)**
- The near-limit chip classes duplicate `rules-list.tsx`'s private `CHIP_NOTICE` (hoist them to a shared ui constant); the screen imported `attempt`, `couldNot` and `figure` from the Recurring screen's `feedback.ts`, whose comments said "Recurring screen" (since moved to `src/app/feedback.ts` with the comments fixed; the moved import's order in `budget-form.tsx` remains).
- The delete failure and not-found paths in `useDeleteBudget` (`delete-budget.tsx`, shared by a card and an upcoming budget) are untested (`renderToStaticMarkup` cannot reach them); the bar has no `role="progressbar"` and there is no text alternative when `percentTenths` is null; the delete confirm has no Escape-to-cancel; the Past months table includes the current month's row (the brief said "every month").

**Form (new and edit)**
- No component-interaction tests (payload mapping, the in-flight no-op, focus on the first invalid field, and the stay-on-the-page path of R8, which only its helpers and a by-eye check cover); `startMonthOptions` reaches only 36 months back and 12 ahead; the import order of the moved feedback import.
- Month labels come in two formats: the form speaks "November 2026" (`monthText`), the server's refusals and the screen speak "Nov 2026" (`monthLabel`), so a person meets both in one flow.
- After a split that stays on the page (R8) the address still names the earlier span. Two upcoming budgets on one ledger give two "Edit <ledger> budget" links with the same accessible name (their visible text says when each starts).

**End-to-end (`tests/e2e/budgets.spec.ts` and the budgets part of `isolation.spec.ts`)**
- Not covered in a browser: a net-refund month, a budget on an archived ledger, the "No budget covers" and "Your budgets start next month" states, ending a budget or switching its rollover through the Settings section, and a phone-width viewport. All but the last are covered below the browser (domain, service and render tests).
- The keyboard spec chooses a month and a ledger by typing into a closed select; Chrome, the suite's only browser, honours that, but it is not a cross-browser guarantee. The reduced-motion check reads the bar's computed `transition-property` and dark mode is checked by the page and heading colours, not by a contrast ratio for each chip.
- The isolation `aimed` helper is copied once more beside the recurring and investment ones, as those are (each describe block owns its own); the dashboard count check relies on A having two budgets over and B one near, so it would need updating if either seed changes.
- No browser test covers the Upcoming list or the not-saved message; both are covered by render and helper tests and were checked by eye (light and dark, desktop and 375px).
- Budget isolation is proved through the browser for the pages and the three actions (revise, settings, delete); creating a budget on A's ledger id is proved in the action and repository tests, not again through the browser.

## What M5 does not do

The design's non-goals, recorded so a later request is not read as a regression.

- **No other kinds of budget.** No income budgets, no budgets on assets, liabilities or investments, no per-tag budgets, no yearly or weekly budgets, and no zero-based planning. A budget is a monthly cap on one expense ledger.
- **No notifications.** No email and no push; the budgets screen, the dashboard line and the warning when recording are the notification.
- **No proration.** A budget created in the middle of a month is measured against its whole amount for that month (EC-48): prorating confuses more than it helps.
- **No forecasts beyond one line.** The single "at this pace" projection is all there is, and the history is a table, not a chart; the only graphic is the progress bar.
- **No change to the Spending report.** It has no budget markers; a budget's figures reconcile with it and with the Transactions screen, but the report is not touched.
- **No pending recurring entries counted.** A proposal in the recurring inbox is not spend until it is posted, so no budget counts it.
