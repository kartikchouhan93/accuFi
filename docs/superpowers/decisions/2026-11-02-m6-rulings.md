# AccuFi M6 — decisions taken during implementation

Every ruling made while executing `docs/superpowers/plans/2026-11-02-accufi-m6-csv-import.md` (CSV import), numbered R1
onward in the order they were made: three made before any task started (while checking that the eleven tasks' interfaces
agreed with each other), then one per task as the ledger records them. Each records what was ruled, why, and what it costs
if it turns out to be wrong. The design is `docs/superpowers/specs/2026-11-02-accufi-m6-csv-import-design.md`.

---

### R1: ImportRow's duplicate and recurring-occurrence links are plain id columns, with no foreign key

What was ruled: `ImportRow.occurrenceId` (the pending recurring occurrence a staged row was matched to) and
`ImportRow.duplicateOfTransactionId` (the live transaction a row probably repeats) are stored as plain text columns,
never as foreign keys.
Why: a pending occurrence is hard-deleted outright when its recurring rule is deleted (M4's `softDeleteRule`), so a
RESTRICT foreign key would stop a rule from ever being deleted while an import row still pointed at one of its
occurrences, and a SET NULL foreign key would silently drop the link with no trace that it ever existed. The duplicate
transaction, for its part, is only ever soft-deleted, and a foreign key to it would add one more circular cleanup edge
to a pair that is already circular (`ImportRow.transactionId` and `Transaction.importRowId` already reference each
other). Both ids are re-checked wherever they matter instead: the review screen re-reads what they point at every time
it loads, and a commit re-checks that a linked occurrence is still PENDING before trusting it, refusing the row
otherwise.
Cost if wrong: a stale id points at nothing. Since every read re-validates rather than trusting the stored id, the
practical effect is that the review screen simply stops showing the duplicate flag or the recurring link — no data is
corrupted, and nothing is ever committed on the strength of an id that no longer resolves.

### R2: An upload that gets back something other than JSON is always told its session expired, never treated as success

What was ruled: the upload form treats any response it cannot parse as JSON — the login page's own HTML after a
redirect, or any other HTML error page — as "Your session has expired. Sign in again and retry.", and never as a
successful upload.
Why: the upload route's own 401 JSON reply is only reachable once the reverse proxy has let the request through in the
first place; a session that was still valid when the proxy checked it but has since expired by the time the route
handler runs would otherwise look like an unexplained parse failure.
Cost if wrong: a signed-out upload shows a generic "something went wrong" message instead of the more accurate sign-in
hint — a worse message, but no file is lost and nothing is recorded either way.

### R3: The 5 MB upload cap is trusted to reach the route handler unclipped, on Next's own documented default

What was ruled: Next's reverse proxy buffers request bodies up to its documented default of 10 MB, which is above the
5 MB import cap, so the cap can be enforced entirely inside the route handler with no extra proxy configuration.
Why: this was a belief drawn from Next 16's documented default, not independently verified against this app's own
deployment; the task that builds the route handler was asked to check the proxy's actual handling of a multipart body
and report what it found. This task's own browser uploads stay well under the cap (small synthetic files), so a
near-cap upload going through the real proxy is still untested end to end.
Cost if wrong: an upload between the proxy's own limit and 5 MB would fail with a worse error message instead of the
handler's clearer "larger than 5 MB" one — the file is refused either way, so not a correctness bug. (Originally
written as "a generic proxy error"; R2's own implementation actually turns that proxy rejection into "Your session has
expired," a specific and more misleading message than this line once assumed — see R9.)

### R4: Staging silently drops a row whose cells are all blank, rather than erroring it

What was ruled: when a staged file is split into rows, a row whose every cell is empty or pure whitespace is dropped
before it ever becomes an `ImportRow` — never shown as an error, never shown at all.
Why: an Excel-style trailing blank line, or a line of nothing but delimiters, is noise a spreadsheet export leaves
behind, not a transaction; turning every one of those into an ERRORED row would bury the real errors on a statement
among rows nobody needs to look at.
Cost if wrong: a row that genuinely was meant to carry a transaction but happens to read as all-blank (a stripped
file, a badly produced export) is silently skipped rather than flagged — but since it carries no data in the first
place, there was nothing it could have recorded regardless.

### R5: A refund — an EXPENSE ledger paying money back INTO an asset account — is a legal import counterpart

What was ruled: a plan test line asserted that an incoming (IN) row from an EXPENSE ledger counterpart was illegal;
`isLegalCounterpart` instead follows the same flow table every other write in the app already uses, which allows
EXPENSE → ASSET — exactly what a refund is — so the test was corrected to assert the row IS legal, not written to
match the plan's mistaken line.
Why: the design spec says refunds exist (EC-20), and an import's counterpart should be no stricter than a
hand-entered transaction's.
Cost if wrong: none in practice — the ruling's effect is that a refund row (a shop crediting money back to a card or
bank account) can be imported and given its real counterpart, which is the correct behaviour either way.

### R6: A duplicate found only at commit is refused and sent back to review, and only that re-flag is written

What was ruled (final whole-branch review, C2): `commitBatch` re-runs `findDuplicate` for every READY row with no
duplicate flag against the account's live transactions as they are at commit. A match refuses the whole commit
(`ImportRowsIllegalError`, naming the line, nothing posted) and, in the same refusing call, moves that row back to
PENDING with `duplicateOfTransactionId` set, so the review screen offers the usual "Import anyway" / "Skip as
duplicate". A READY row that already carries a duplicate flag was imported anyway on purpose and is never re-checked.
Why: staging only sees the ledger as it was then, so two overlapping statements staged before either was committed, or
an entry typed or auto-posted in between, would otherwise post twice with no warning; refusing without the re-flag
would leave the person in a refusal loop with nothing on screen to act on.
Cost if wrong: a refused commit writes one thing (the re-flag) instead of nothing — a row-level review state, never a
transaction or a balance.

### R7: Import without Link always unlinks, on the server; a linked row whose ledger and rule disagree is refused

What was ruled (final review, C1): `updateRow` with `decision: "IMPORT"` and no `occurrence: "LINK"` clears the row's
`occurrenceId` itself, whatever the caller sent; LINK with a different explicit ledger is refused; "Confirm suggested
ledgers" skips occurrence-matched rows; and `commitBatch` refuses a linked row whose stored counterpart is not its
rule's ledger instead of silently using the rule's. A plain Import with no ledger of its own is refused rather than
quietly linked.
Why: the counterpart prefill and the occurrence match are computed independently at staging, so a row could show one
ledger and post to another; correctness must not depend on one client call site remembering to send UNLINK.
Cost if wrong: a person who wanted the recurring link must press "Link to …" explicitly — one extra, deliberate click.

### R8: Commit's duplicate re-check (R6) closes the sequential case, not the concurrent one — accepted as a known gap

What was ruled (final whole-branch review fix wave, re-reviewed): R6's re-check at commit catches a duplicate created by
staging-then-committing in sequence, or by an entry made between staging and commit. It does not catch a transaction
that commits *while this commit is still running* — another tab committing an overlapping batch against the same
account, or the hourly recurring sweep posting an occurrence — because no part of the app takes an account-level lock
and Postgres runs at READ COMMITTED. This is accepted as a known residual gap, not fixed in this round.
Why: closing it fully means locking the account node itself inside `commitBatch` (the same pattern
`budget-repository.ts` already uses for its own guarded writes), which is a real, scoped follow-up but not one to rush
into the same fix wave that just changed this function twice; the gap only opens under genuine concurrent writes to one
account from the same person, which is a narrow window compared to the sequential case R6 already closes.
Cost if wrong: a rare double-post from two truly concurrent writes to the same account. Nothing is silently
unrecoverable — reversing either batch restores the exact prior balance — but the person would need to notice the
duplicate and reverse it themselves; it is not caught automatically the way the sequential case is.

**Partially closed (follow-up pass):** `commitBatch` now takes `lockLedger(userId, batch.nodeId, uow)` — the same
`budget-repository.ts` function `lockedSpans` already uses, reused rather than duplicated — right after confirming the
batch is STAGED and before re-checking duplicates. Two different batches against the same account, committed at the
same time, now serialise: the second waits for the first, then re-reads the ledger as the first left it, and
`findDuplicatesSinceStaging` catches the overlap exactly as it already does for the sequential case (R6). Proven by a
race test in `tests/server/imports/commit.test.ts` ("final review R8") that fails — both commits succeed, the
duplicate posts twice — with the lock removed.
This closes the commit-vs-commit half of the gap, not the commit-vs-sweep half: `postOccurrence`
(`occurrence-service.ts`) → `recordTransaction` (`transaction-service.ts`) still takes no node lock before writing (only
`lockLotHoldings`, for investment nodes specifically), so the recurring sweep posting an occurrence against the same
account while a commit is mid-flight is still unserialised against it. Closing that needs the equivalent lock inside
`recordTransaction` itself — which guards every transaction write in the app, not only import's, and has its own
lock-ordering question against the budget and investment locks already taken elsewhere — so it is left as its own,
separately-scoped follow-up rather than folded in here.

### R9: A proxy's own HTML rejection (not just a lapsed session) is shown as "Your session has expired" — accepted as a known UX gap

What was ruled (final whole-branch review fix wave, re-reviewed): the upload form treats *any* non-JSON response as a
lapsed session (R2), with no way to tell a login-page redirect apart from a reverse proxy's own HTML error page — most
concretely, a proxy-level 413 when the uploaded file exceeds a proxy body-size limit smaller than this app's own 5 MB
cap. The README's own suggested nginx configuration example defaults to a 1 MB limit, so in that documented setup every
statement over 1 MB would show the sign-in message on every retry, never the real reason.
Why: accepted rather than fixed now, because no data or money is at risk — the upload simply never succeeds, and the
person sees a wrong-but-safe message rather than silent corruption or a stuck server state. The actual fix (check
`response.redirected` against `/login`, or the response's status, before assuming "expired") is small and local but
changes behaviour R2 already committed to, so it is left for its own pass rather than folded into this fix wave.
Cost if wrong: a confusing, repeatable error message for anyone whose statement exceeds a smaller-than-5 MB proxy
limit; no data loss, no wrong transaction, and R3's "cost if wrong" (below) should be read alongside this one — it
no longer means a *generic* proxy error, it means this specific, misleading one.

**Closed (follow-up pass):** `readUploadResponse` (`upload-response.ts`) no longer treats every non-JSON answer alike.
A real login-page landing is always a followed redirect's final 200 (`response.redirected` is not readable on a
constructed `Response` in a unit test, so status is the testable signal the ruling's own text already named as an
alternative), so a non-JSON body at status 200 is still read as `{ kind: "expired" }` exactly as before; a non-JSON
body at any other status is now its own outcome, `{ kind: "blocked", status }`, which the upload form shows as "A
server in front of this app rejected the file as too large" for a 413, or "The server rejected the request (status
…)" otherwise — never the sign-in message. Covered in `upload-response.test.ts` ("ruling R9") for 413, 502 and a
bodyless 500.

## Known and parked

Found during implementation or review and left alone on purpose, so a later reader does not mistake them for
oversights. None of it puts money, another user's data, or a wrong transaction at risk — each is a gap in test
coverage, a wording nit, or a low-probability edge documented rather than fixed. Grouped by where it lives.

**Decoding, parsing and matching (`src/domain/import-csv.ts`, `import-map.ts`, `import-match.ts`)**
- Windows-1252's five undefined byte values (0x81 and similar, which map to C1 control characters and still decode
  without error) are not pinned by a test; the "no byte of the file ever reaches an error message" claim is checked
  only for one accented character, not asserted as the exact fixed string everywhere it could matter.
- A Dr/Cr suffix that contradicts the column it is in (a "Dr" written in the credit column, or a "Cr" in the debit
  column) is read as the column's own direction rather than flagged as an error; leading zeros in a grouped amount
  ("0,100" or "01,000") are silently accepted; `YYYY-MM-DD` accepts an unpadded month or day ("2026-4-3") with no test
  recording that this is intended; there is no test for 29 February 2100 (not a leap year), for a year written with
  fewer than four digits, for a signed debit amount, for "(500) Dr", or for a `descriptionKey` truncation landing
  inside a two-character emoji or other surrogate pair.
- Two learned rules with the identical description key but different ledgers would only ever resolve by whichever the
  database happens to return first, since a row's own constraints prevent having two to begin with; "longest matching
  rule wins" is measured in characters, not words, which the code does not say out loud. Several matching edge cases
  (an exact tie broken alphabetically, a rule whose tokens are present but scattered rather than contiguous, two rows
  competing for the same recurring occurrence, and a counterpart that is itself an un-lotted investment) are reasoned
  about but not separately tested.

**Database schema (`prisma/schema.prisma`, the `csv_import` migration)**
- The tests proving a RESTRICT foreign key refuses a delete check only that the attempt throws, not that it throws the
  database's own foreign-key error specifically; the test for deleting a user with import data is close to a no-op
  since other foreign keys already block it first; deleting a whole batch is not proven to leave an unrelated
  transaction's `importBatchId` alone; and the direction that proves `ImportRow.transactionId` itself is RESTRICT is
  untested. The CHECK-violation test helper matches on the generic phrase "check constraint" rather than the specific
  constraint's name. The design document does not yet note that `ImportBatch.profileId` is SET NULL on delete, a
  deliberate choice made while writing the migration.

**Repository layer (`src/server/repositories/import-repository.ts`)**
- `updateRow` and the bulk `updateRowsWhereSame` accept any caller-supplied status, including COMMITTED or ERRORED,
  which only the database's own CHECK constraint would catch (as a raw error, not a clean refusal) if a caller ever
  passed one by mistake; narrowing the accepted type would catch it at compile time instead. (`markRowsCommitted` once
  updated one row at a time; since the final review it is one set-based statement.) The check that an import's two foreign ids both belong to the caller does not also
  check that they belong to the SAME batch, so in principle a row from one batch could be paired with a transaction id
  from another. `upsertProfile` passes a JavaScript `null` where Prisma expects its own null marker for a JSON column.
  A couple of isolation tests for profiles and learned rules are weaker than the exact-leak style used elsewhere in the
  suite, and `findRows`' paging accepts an out-of-range offset or limit without clamping it the way an equivalent
  lookup elsewhere in the app already does.

**Staging (`stageBatch`, in `import-service.ts`)**
- Listing every ledger for the counterpart suggestion runs outside the batch's own row lock, the same pattern as one
  other lookup staging already makes outside the lock — harmless here, since it only affects which ledger is
  pre-filled, never a row's actual status. A validation message for a split amount mapping always blames the "amount"
  field even when the real problem is a missing credit column. Reading the header row when more than one row is
  skipped at the top of the file is untested.

**Review operations (`updateRow`, `applyCounterpartToSimilar`, `confirmSuggestions`, in `import-service.ts`)**
- One item once parked here is withdrawn: a doc comment that was accidentally attached to the wrong function was moved
  back to the right one during the final whole-branch review's fix wave. "Confirm suggested ledgers" now skips any row
  matched to a recurring entry (R7), which means it can leave more rows `PENDING` than before, even when the prefilled
  ledger already happens to match the rule's own — a deliberate trade-off for correctness, not a defect. It also now
  runs one short, locked statement per row rather than a single batched update; on a very large batch this is slower
  (not unsafe — there is no single long transaction, so no timeout risk, just more round trips), and a single
  `updateMany` under one shared lock would be a cheap improvement when convenient.

**Commit and reversal (`commitBatch`, `reverseBatch`, in `import-service.ts`)**
- The concurrent-writer gap in R6's duplicate re-check, and the proxy-413-as-"session-expired" gap in R2, are both
  tracked as their own rulings now (R8, R9) rather than left as loose parked items, since the final whole-branch review
  judged each worth a named decision, not just a note.
- A row decision (Import, Skip, a counterpart change, "Confirm suggested ledgers") now takes a share lock on the batch
  so it waits for an in-progress commit rather than racing it (fixed during the final review). That wait uses the
  database's ordinary interactive-transaction timeout, so a decision or a "Confirm suggested ledgers" call that happens
  to overlap an unusually long commit can surface as a generic "check your connection" error instead of a clean
  refusal — safe (nothing is written either way), just a worse message in a rare, narrow window.
- A row the person explicitly chose to "Import anyway" despite a flagged duplicate is correctly never re-checked
  against *that same* matched transaction at commit (R6) — but it is also not re-checked against a *different*,
  later transaction that happens to duplicate it too (for instance a second overlapping statement committed in
  between). Narrowing R6's re-check to look only at the one duplicate the person already decided on, rather than
  excluding the row entirely, would close this; not done in this pass.
- One error's doc comment describes the wrong condition (it says "not STAGED or COMMITTED" when it means "rows are
  still pending a decision"). There is no test for the rare case where a linked recurring occurrence changes under a
  commit already in progress. A few edges are reasoned about but not separately tested: a counterpart under the
  overdraft guard, the review screen's own view of a batch mid-commit, and one investor's balance in the reversal test.
  (Two items once parked here were wrong and are withdrawn, per the final whole-branch review: the failed-commit test
  in `tests/server/imports/commit.test.ts` ("review focus 2") fails only after two real inserts have been made inside
  the commit's own transaction, so it genuinely proves the rollback; and a counterpart archived between staging and
  committing is tested directly by that file's "review focus 3" archived-counterpart test.) A counterpart that somehow does not resolve at all surfaces a generic "not found"
  rather than a message naming the row's line (this path is not reachable today, since the database's own foreign
  keys and validation already rule it out beforehand). The error listing every illegal row joins them with no limit,
  so an unusually large batch could in principle produce a very long message. The ledger-delete check for an import
  runs outside its own delete transaction, the same small, pre-existing timing gap the equivalent checks for a
  recurring rule or a budget already have. The commit transaction's own timeout (about three and a half minutes, sized
  for the maximum 20,000-row batch) is an upper bound, not an expected duration — a commit that somehow got stuck would
  hold a database connection and the batch's row lock for that whole span against the pool. **Carried forward to the
  final whole-branch review, not just a historical note:** `import-service.ts` now runs to over a thousand lines
  covering upload, mapping, staging, review, commit and reversal together; commit and reversal (and probably the
  review operations alongside them) should be split out into their own module rather than staying in the same file.
  This was flagged during Task 8's review as something to revisit once the whole branch is in view, not something to
  fix mid-task. Separately, and lower-stakes: the batch filter the transactions screen accepts is a plain string with
  no length bound enforced anywhere — harmless today since it only ever holds a user-scoped batch id, but worth a
  second look alongside the module split.

**Actions, the upload route and loaders (`import-service.ts`'s loaders, `actions.ts`, `route.ts`)**
- The message format for a commit refused over six or more illegal rows at once (five shown, then "and N more") went
  untested until a dedicated test was added in a later fix round; it is covered now. The "file is larger than 5 MB"
  wording is kept in two places (the route's own size check and the general failure-mapping table) with no shared
  constant, so the two have to be kept in sync by hand; in practice the route's own check always answers first, so the
  failure-mapping table's copy of that message is never actually exercised. A batch whose account ledger has somehow
  been deleted is handled inconsistently between two loaders (one throws, one falls back to showing "Unknown
  account"), a difference that was not reconciled.

**Upload and mapping screen (`/import/new`, `/import/[id]/map`)**
- The Stage button is visually and semantically dimmed (`aria-disabled`) when the file could not be decoded, but
  nothing stops a keyboard activation or a scripted click from reaching the server regardless — the server's own
  staging rejects an undecodable file either way, so this is a defence-in-depth gap, not a way to stage something
  broken. The preview table's screen-reader-only caption always says "first 20 rows", even for a shorter file, while
  the sighted text above it correctly says how many rows there really are.

**Review and batch screens (`/import/[id]/review`, `/import/[id]/batch`)**
- The render test proving a counterpart choice is legal exercises only an ASSET account, not a LIABILITY one, though
  the underlying domain rule is already tested both ways elsewhere. The batch page's own "reverse, with a confirm"
  interaction is written as its own, separate copy of the same shape the review screen's commit bar already uses,
  rather than a shared piece — consistent with how the rest of the codebase keeps one copy per screen rather than
  factoring early.

## What M6 does not do

The design's own non-goals (§2), recorded here so a later request for one of these is read as new work, not as a
regression.

- **CSV only.** No bank APIs, account aggregators, OFX, QIF, PDF or Excel input — a statement must be a CSV file.
- **No auto-detection.** The delimiter, the text encoding and the date format are never guessed from the file; the
  preview shows the effect of whatever is chosen, and the person makes the choice.
- **No splitting a row, and no investment movements.** One statement row becomes one transaction between the account
  and one counterpart, never several; buying or selling an investment held by lots cannot be imported (nothing can be
  moved into or out of a lot-mode holding this way), and a statement's own running balance or "closing balance" line
  is never read or checked against anything.
- **Duplicates are only ever checked against the ledger, never within the file itself.** Two identical coffees on the
  same day, both in the same upload, are left as two ordinary rows — only a match against an existing, already-recorded
  transaction is flagged. Duplicate matching itself stays exactly date ±3 days, same amount, same direction; nothing
  fuzzier is attempted.
- **No management screen for what an import has learned**, no scheduled or recurring imports, no importing by email,
  and no bulk re-categorising of transactions an import already committed.
- **Nothing elsewhere changes beyond what the design's §7 lists** for recurring entries, budgets, or the Transactions
  screen.
