# AccuFi M4 — decisions taken during implementation

Every ruling made while executing `docs/superpowers/plans/2026-10-28-accufi-m4-recurring.md` (recurring entries),
numbered R1 onward in the order they were made. Each records what was ruled or run, the evidence, and the outcome.

---

### R1: The sweep timer runs under `bun --bun run start`, so the cron fallback is not needed

What was run: design §11 names the production runtime as the risk to settle first, because the container starts the
app with `bun --bun run start`. `src/instrumentation.ts` exports `register()`, which (on `NEXT_RUNTIME === "nodejs"`)
starts `startSweepTimer` from `src/server/sweep-timer.ts` with a stub run function that logs `[recurring-sweep] tick`.
After `bun run build`, on the host against the dev database (the stub does not touch it), port 3301:

```
$ RECURRING_SWEEP_INTERVAL_MS=2000 bun --bun run start -p 3301     # killed after about 7 seconds
$ next start -p "3301"
▲ Next.js 16.1.3
✓ Starting...
[recurring-sweep] tick
✓ Ready in 193ms
[recurring-sweep] tick
[recurring-sweep] tick
[recurring-sweep] tick

$ RECURRING_SWEEP=off RECURRING_SWEEP_INTERVAL_MS=2000 bun --bun run start -p 3301     # same 7 seconds
$ next start -p "3301"
▲ Next.js 16.1.3
✓ Starting...
✓ Ready in 133ms
```

Versions: Bun 1.4.3 (the Dockerfile's `oven/bun:1.4.3` pin), Next.js 16.1.3.

Outcome: `register()` ran, the first tick fired at startup (before "Ready"), and two more fired at the 2 s interval; the
timer stayed alive for the whole run despite being `unref`'d (the HTTP server keeps the process up). With
`RECURRING_SWEEP=off` there were no ticks. The in-process timer is therefore the mechanism. The `POST` route fallback
(design §11) was not built.
Caveat: this ran on the host with Bun as the runtime, not inside the Docker image; the image uses the same Bun version and
start command, and `NEXT_RUNTIME` is `nodejs` under `next start` in both.
Cost if wrong: one secret-guarded route and a README line (the design's fallback), nothing else changes.

### R2: Tests control "today" with fake `Date` timers, as the report tests do

What was ruled: tests that need a fixed day use `vi.useFakeTimers({ toFake: ["Date"], now })`, the pattern of `tests/server/reports/flow-reports.test.ts`. No other clock seam exists, and the plan's "clock helper pattern" means this one.
Cost if wrong: add a clock seam to `src/server/services/clock.ts` (small).

### R3: A rule with no date left has its next due day cleared

What was ruled: in `generateDue`, when `datesDue` from `nextDueOn` returns no date (the occurrence limit or the end date has been reached, or an edit moved the end behind it), `nextDueOn` is set to null instead of being left in the past.
Why: a rule left "due" forever would be scanned again by every sweep. Cost: nothing.

### R4: The month-end end-to-end test gives the day-31 rule an end date of 30 April 2026

What was ruled: the rule runs monthly on the 31st from 31 January 2026 with an end date of 30 April 2026, so the inbox holds exactly four cards (31 Jan, 28 Feb, 31 Mar, 30 Apr). The real date is later than April 2026, so all four are past.
Why: the plan's "through 30 April" needs an end to stop generation at; without one the rule would go on proposing up to today. Cost: none.

### R5: Component tests are `.test.ts` files that render with the existing render-test approach

What was ruled: tests of components live as `.test.ts` (no JSX files), rendering the way the repository's other render tests do. Vitest includes `tests/**` and `src/**`.
Cost: none; it matches the repository.

### R6: An occurrence of a deleted rule is not found by post, skip or put back

What was ruled: the repository stays as it is. The occurrence service treats an occurrence whose rule has `deletedAt` set as `NotFoundError` in post, dismiss and restore, and a test pins it, so a skipped entry of a deleted rule cannot be revived.
Cost if wrong: add `rule: { is: { deletedAt: null } }` to `markPending` and `markPosted` in the repository (small).

### R7: Recently handled lists only the entries of live rules

What was ruled: `loadRecurringScreen` reads recently handled entries with `liveRulesOnly`. A deleted rule's skipped entry cannot be put back (the service says not found), so listing it would offer a button that cannot work. Its posted and skipped rows stay in the table as history (EC-45).
Cost if wrong: drop the flag at the `findRecentlyHandled` call in `loadRecurringScreen` (one line).

## Known and parked

Found in review and left alone on purpose, none of it a risk to money or to another user's data. Grouped by where it is.

**History and the ledger**
- Deleting the transaction behind a posted entry leaves the entry posted (EC-45): it is history, and the Recently handled row still shows what was recorded.
- A crash between committing the generated entries and auto-posting leaves an auto-post entry silently pending, with no "not posted automatically" note; nothing retries it, the money is safe and the entry is in the inbox.
- One failing rule aborts the rest of that user's rules for the run (wrapping each rule's generation and auto-post in its own try/catch would stop that); the next run carries on.

**Sweep timer**
- No guard against a second `register()` call (two timers), and `stop()` is not wired to shutdown; `intervalMs` against the environment's precedence and `unref` are untested; a throwing injected logger would leave an unhandled rejection (theoretical).
- The programmatic `intervalMs` option is not bounded by the 2147483647 ceiling (only the environment path is), and the README does not state the ceiling.

**Schedule arithmetic (`src/domain/recurrence.ts`)**
- `datesDue` accepts an interval of 1.5 or Infinity (should be `Number.isInteger`), and a day of month of 0 or less throws from `calendarDate` instead of returning no dates; its defensive `??` defaults repeat `normaliseSchedule` and need a comment; a few lines run past 120 characters.
- The schedule mapping is written three times (`scheduleOf` in `recurring-generation.ts`, `scheduleOfRule` in `recurring-view.ts`, a copy in a test): delete the copies and import `scheduleOfRule`.

**Schema and repository**
- The due-scan index `(userId, nextDueOn)` does not serve the global sweep query `findUsersWithRulesDueBy`; the table is tiny at personal scale, and `(nextDueOn)` can be added if it ever matters.
- The migration comment says "like every other FK" though `parentId` and `groupId` are `SET NULL`; no test asserts that the `RecurringRule` `updated_at` trigger fires.
- `mark*` and `insertOccurrences` do not themselves require a live rule (the service closes that, see R6); `markPosted` accepts a soft-deleted transaction; `findUsersWithRulesDueBy` uses `distinct` where `groupBy` would push the dedupe into SQL; `findOccurrenceById` and `findRecentlyHandled` do not scope the rule join by user (safe, since occurrences are only inserted for the user's own rules); `findRecentlyHandled` accepts an unbounded or non-finite limit; the duplicate-key lookup runs inside an uncommitted unit of work.
- Two repository isolation cases depend on file order, and the concurrent-insert test is probabilistic.

**Occurrence and rule services**
- The message for a skip that lands between the read and the mark should say the transaction was recorded; the QUANTITY predicate is written twice (`recurring-view.ts` and `lotModeOf`) with no parity test; the soft-deleted-transaction fallback by idempotency key, the `markPosted`-null re-read branch and the paused-or-deleted re-checks after the lock have no direct test.
- A sweep that moves `nextDueOn` bumps the rule's version, so an edit form open at that moment meets a conflict and reloads (accepted, safe).
- `editRule` validates an archived end strictly, so a blocked rule cannot be renamed; `createRule` throws if `generateDue` fails after the insert (it could fall back to the stored rule); the `setPaused` retry path is untested and wants a comment; a replay of a soft-deleted rule's key returns that rule; `editRule` validates before it checks the rule exists; one comment (`anchorField`) is stale.

**Actions and loaders**
- `pauseRuleSchema` is dead code; the investments and nodes actions still carry their own copies of `parseInput` and `violationFieldErrors`; the result-shape check for bigint leaks covers success results only, not conflicts and field errors; `loadRecurringScreen` reads without a snapshot, so a node created mid-read could throw (negligible); the archived-end and lot-purchase cases of `templateFromTransaction` are untested; there is no loader test for the posted branch of `recent` or for a mix of live and deleted rules.

**Inbox and rules screen**
- Post on a quantity entry while its form is open does nothing, though `aria-expanded` suggests a toggle; Pause, Resume and Delete drop keyboard focus while pending (`aria-disabled` would keep it) and lack the in-flight guard the cards have; the reason an archived entry cannot be posted is visible text only, and disabled buttons are skipped by Tab.
- `putBack` is imported from `recent-list.tsx` (it belongs in `feedback.ts`) and `inbox-card.tsx` is about 400 lines; an animation-frame focus is not cancelled on unmount; one test reads the source with a regular expression; there is no interaction test for the quantity focus; the narrow-screen case of a long amount beside a long name was checked at desktop width only.

**Rule form**
- The submit logic (request-key reuse, `expectedVersion`, the conflict branch, the payload shape, the redirect) has no unit test of its own; the end-to-end suite covers creating, not conflicts.
- The "over 100 entries" line reads like a promise although the server refuses it; it should say there are too many to create at once and to pick a later start.
- "Make recurring" loses the 31st: the draft carries no day of month, so a transaction on 31 March becomes a rule on the 30th for good.
- A stale "Reloaded" flash can persist in session storage if the reload 404s; the automatic-posting helper text is not tied to its control by `aria-describedby` (the reason id is unused); `startOpen` is a test-only prop on the production `EntryRow`; small nits (a `maxLength` of 500 repeating `NOTE_MAX_LENGTH`, a `CalendarDate` cast, a test asserting a class name, a misnamed render test, a Fragment's indentation).

## What M4 does not do

The design's non-goals, recorded so a later request is not read as a regression.

- **No bulk actions.** There is no "post all"; every entry is posted, changed or skipped on its own card.
- **No calendar view.** The inbox is a list, oldest first, and the rules are a list.
- **No split templates, and no EMI.** A rule is one two-sided transaction; a loan payment split into principal and interest is not a rule (`GroupKind.EMI` stays unused).
- **No notifications.** No email and no push; the inbox, the navigation badge and the dashboard notice are the notification.
- **No forecasts.** No projected balance, and a pending entry is counted in no figure: not a balance, not net worth, not a report.
- **No "from rule" chip** on the Transactions list. The link from a posted entry to its rule exists in the table; showing it is a later request.
- **No RRULE strings or irregular schedules.** The structured schedule is the decision; RRULE is the upgrade path.
- **No budgets and no CSV import**, and so no matching of imports to pending entries (M5 and M6).
