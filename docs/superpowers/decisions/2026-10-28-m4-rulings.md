# AccuFi M4 — decisions taken during implementation

Every ruling made while executing `docs/superpowers/plans/2026-10-28-accufi-m4-recurring.md` (recurring entries),
numbered R1 onward in the order they were made. Each records what was ruled or run, the evidence, and the outcome.

---

### R1: The sweep timer runs under `bun --bun run start`, so the cron fallback is not needed

What was run: design §11 names the production runtime as the risk to settle first, because the container starts the
app with `bun --bun run start`. `src/instrumentation.ts` exports `register()`, which (on `NEXT_RUNTIME === "nodejs"`)
starts `startSweepTimer` from `src/server/sweep-timer.ts` with a stub run function that logs `[recurring-sweep] tick`.
After `bun run build`, on the host against the dev database (the stub does not touch it), port 3301:

```
$ RECURRING_SWEEP_INTERVAL_MS=2000 bun --bun run start -p 3301     # killed after about 7 seconds
$ next start -p "3301"
▲ Next.js 16.1.3
✓ Starting...
[recurring-sweep] tick
✓ Ready in 193ms
[recurring-sweep] tick
[recurring-sweep] tick
[recurring-sweep] tick

$ RECURRING_SWEEP=off RECURRING_SWEEP_INTERVAL_MS=2000 bun --bun run start -p 3301     # same 7 seconds
$ next start -p "3301"
▲ Next.js 16.1.3
✓ Starting...
✓ Ready in 133ms
```

Versions: Bun 1.4.3 (the Dockerfile's `oven/bun:1.4.3` pin), Next.js 16.1.3.

Outcome: `register()` ran, the first tick fired at startup (before "Ready"), and two more fired at the 2 s interval; the
timer stayed alive for the whole run despite being `unref`'d (the HTTP server keeps the process up). With
`RECURRING_SWEEP=off` there were no ticks. The in-process timer is therefore the mechanism. The `POST` route fallback
(design §11) was not built.
Caveat: this ran on the host with Bun as the runtime, not inside the Docker image; the image uses the same Bun version and
start command, and `NEXT_RUNTIME` is `nodejs` under `next start` in both.
Cost if wrong: one secret-guarded route and a README line (the design's fallback), nothing else changes.

### R2: Tests control "today" with fake `Date` timers, as the report tests do

What was ruled: tests that need a fixed day use `vi.useFakeTimers({ toFake: ["Date"], now })`, the pattern of `tests/server/reports/flow-reports.test.ts`. No other clock seam exists, and the plan's "clock helper pattern" means this one.
Cost if wrong: add a clock seam to `src/server/services/clock.ts` (small).

### R3: A rule with no date left has its next due day cleared

What was ruled: in `generateDue`, when `datesDue` from `nextDueOn` returns no date (the occurrence limit or the end date has been reached, or an edit moved the end behind it), `nextDueOn` is set to null instead of being left in the past.
Why: a rule left "due" forever would be scanned again by every sweep. Cost: nothing.

### R4: The month-end end-to-end test gives the day-31 rule an end date of 30 April 2026

What was ruled: the rule runs monthly on the 31st from 31 January 2026 with an end date of 30 April 2026, so the inbox holds exactly four cards (31 Jan, 28 Feb, 31 Mar, 30 Apr). The real date is later than April 2026, so all four are past.
Why: the plan's "through 30 April" needs an end to stop generation at; without one the rule would go on proposing up to today. Cost: none.

### R5: Component tests are `.test.ts` files that render with the existing render-test approach

What was ruled: tests of components live as `.test.ts` (no JSX files), rendering the way the repository's other render tests do. Vitest includes `tests/**` and `src/**`.
Cost: none; it matches the repository.

### R6: An occurrence of a deleted rule is not found by post, skip or put back

What was ruled: the repository stays as it is. The occurrence service treats an occurrence whose rule has `deletedAt` set as `NotFoundError` in post, dismiss and restore, and a test pins it, so a skipped entry of a deleted rule cannot be revived.
Cost if wrong: add `rule: { is: { deletedAt: null } }` to `markPending` and `markPosted` in the repository (small).

### R7: Recently handled lists only the entries of live rules

What was ruled: `loadRecurringScreen` reads recently handled entries with `liveRulesOnly`. A deleted rule's skipped entry cannot be put back (the service says not found), so listing it would offer a button that cannot work. Its posted and skipped rows stay in the table as history (EC-45).
Cost if wrong: drop the flag at the `findRecentlyHandled` call in `loadRecurringScreen` (one line).

### R8: The real `sweepAll` runs under `next start`, against the test database

What was run: R1 proved the timer with a stub. This ran the real `sweepAll` from the production build, on the host with Bun as
the runtime, against the test database only (`accufi_test`, the sibling of the dev database; the dev database and the Docker
app on port 3100 were not touched). A throwaway user got one rule through `createRule` (weekly, starting today, so its own
generation made its one entry) and a second rule inserted straight through Prisma, weekly, due two weeks ago, with no
occurrences, so that only a sweep could make them. The sweep interval was 5 s; the server was started before the rules existed,
so its startup tick had nothing to do and a later tick had to find them.

```

$ DATABASE_URL=<test database> AUTH_URL=http://localhost:3301 RECURRING_SWEEP_INTERVAL_MS=5000 bun --bun run start -p 3301

✓ Starting...
```

Outcome: the second rule had no occurrences when it was inserted and three PENDING ones about 1.3 s later, all from one

was free afterwards, and the throwaway user and everything it owned were deleted. Nothing is logged by a successful sweep
(only `[recurring-sweep] tick` was the stub's), so the evidence is the database.
Cost if wrong: none; this only confirms R1's conclusion for the real function.

### R9: A replay of `createRule` for a rule that was made and then deleted is refused, not returned

What was ruled: `createRule` looks the rule up by `(user, request key)` before validating anything (`findRuleByKey`). A live
stored rule is answered as the rules screen would show it now, after generating whatever is due for it. A stored rule that
has since been deleted is not handed back as if it were live: the request is refused as an `InvalidRuleError` filed under the
request key ("This rule was already created and then deleted. Open a new form to create it again."), and nothing is created.
Why: the alternatives were worse. Falling through to create would put a second rule under a key that already has one (the
unique index refuses it), and returning the deleted rule made the user's screen announce a rule that is not there. The form
that sent the request has the key in its state, so the only way to see this is a stale retry; a fresh form has a fresh key.
The loser of a double-click race answers the same way, from a re-read after generation, so its version and next due day are
the stored ones and not those of the row as it was inserted.
Cost if wrong: change one branch in `replayOf` (`src/server/services/recurring-service.ts`).

### R10: A rule that ran out of dates opens its edit form on its last real occurrence; a paused rule is not held to the too-many-due check

What was ruled: (a) a paused rule skips the "more than 100 due now" check on edit, because it generates nothing while paused
and resuming recomputes where it stands from after today (`setPaused`), so a stale date (a daily rule paused for months)
cannot put anything in the inbox. The edit form says "It is paused, so it makes no entries until you resume it." instead of
counting entries. (b) A rule with no next due day (its end date or its occurrence limit was reached) opens its form on the due
day of its LAST real occurrence, in any state and on or before its end date (R17): `loadRuleForEdit` returns it as `lastDueOn` (`findLastDueOn`, a query scoped to
the user) and `valuesOfRule` offers it as "Next due on". An edit re-anchors the schedule on that date, so the grid starts on a
day the rule already has: the unique (rule, due day) keeps it from being made twice, the next date is past the end (or the
limit is spent), and the rule stays ended. A rule that never made an entry is offered today, or its end date if that is
before today.
This replaces the first ruling, which offered the end date and claimed nothing was proposed twice. That held only when the end
date was itself one of the rule's dates: otherwise the grid started on the end date, which is on or before the end and in the
past, so the save (even a rename) made a pending entry the schedule never had, and recorded a transaction if automatic posting
was on (every 2 days from 1 April to 30 April, whose dates end on the 29th; quarterly on the 1st from 1 January to 1 June;
fortnightly on Mondays from 2 March to 6 April). The same cause made a rule with no next due day but an end date still ahead
(every 3 days ending tomorrow) offer today and propose an entry today. The last real date is read from the occurrences, not worked out by
walking the schedule (thousands of days for a long daily rule).
Not done: a rule blocked by an archived account has the same stale-date problem if it is a daily rule more than 100 days
behind, and its edit is still refused; see "Known and parked".
Cost if wrong: `valuesOfRule` and `loadRuleForEdit`, and the `lastDueOn` branch in `editRule`.

### R11: Post sends what the card showed, the form too

What was ruled: the one-tap Post sends the card's amount (its paise as rupee text, never through a number) and note (an empty
note when the card had none) as overrides, instead of the id alone, so a rule edited in another tab since the card was drawn
cannot change what is recorded. The "Edit and post" form was made to match: it sends the amount and note it holds as they
stand, where it used to send only what differed from the card (so an untouched field fell back to the rule's current value,
the same staleness). The day is sent only when changed (an untouched day is the occurrence's own and cannot go stale).
A bare id still records the rule's current template, which is what a client that sends no overrides gets.
Not done: tags are not overridable (the post schema has no tags field), so a rule's tags edited since are the ones recorded;
see "Known and parked".
Cost if wrong: `postPayload` in `src/app/recurring/rule-fields.ts`.

### R12: Deleting an account a rule names is refused through the existing "invalid" refusal

What was ruled: `removeLedgerNode` counts the rules naming the node, at either end, soft-deleted ones included (a deleted rule
stays in the table and its foreign keys are RESTRICT), and refuses with `NodeInRecurringRuleError`, "A recurring rule uses
this account. Archive it instead.". The action returns it as `{ ok: false, error: { code: "invalid" } }`, not as
`has_history`: the nodes screen words `has_history` itself as "This has transactions...", which would be wrong here, and it
shows the service's message for `invalid`. A new code would have meant a new case in every exhaustive switch over the codes.
Cost if wrong: add a code and a case in `node-failure.ts` and `transaction-failure.ts`.

### R13: A post that loses a race to a skip or a delete says it was recorded, and leaves the skip alone

What was ruled: when the occurrence is no longer pending after `recordTransaction` has committed, and it is now skipped or its
rule is deleted, the message says the transaction WAS recorded and where to look ("It was recorded before the skip landed:
check Transactions. Putting it back and posting again will not record it twice."; the deleted-rule wording says the entry
itself is gone). The occurrence is left as the other tab left it. Putting a skipped one back and posting again replays the
same key `recurring:<id>`, so it links to the existing transaction; a test pins that nothing is recorded twice.
Cost if wrong: two strings in `occurrence-service.ts`.

### R14: The pending count is zero when it cannot be read, for the dashboard as well as the shell

What was ruled: `pendingCount(userId)` (`src/app/pending-count.ts`) is `cache()`d, so the shell and the dashboard make one read
per request, and catches a failure: it logs `[recurring] could not read the number of waiting entries; showing none` and
answers 0, so no badge and no dashboard notice, and every page still renders. The failure is cached for the request too, so it
is logged once. The dashboard uses the same helper rather than failing where the shell does not: the notice is as much an
ornament as the badge.
Cost if wrong: let the dashboard read `countPendingFor` directly (it would then error on a failure).

### R15: A failing rule is logged under `[recurring-sweep]`, left due, and the user's other rules carry on

What was ruled: `generateDue` wraps each rule's generation and auto-post in its own try/catch and logs
`[recurring-sweep] generation failed for rule <id>` with the error (the prefix the brief named; the same function also serves a
sign-in and a save, where the prefix reads oddly but is the one to grep for). The rule's transaction rolls back, so its next due
day is unchanged and the next run retries it. What the other rules made is counted. A failure to read today or the list of due
rules is not a rule's and still throws.
Cost if wrong: remove the try/catch.

### R16: "Make recurring" carries the transaction's day of the month, and the nav link's name is one `aria-label`

What was ruled: the draft has the transaction's own day as `dayOfMonth` and the form submits it, so 31 Jan gives 28 Feb, 31 Mar,
30 Apr (the start date stays the clamped day, 28 Feb, since that is the first real date). The Recurring link's accessible name
is `aria-label="Recurring, N waiting"` instead of a label and a screen-reader span, which the browser joined with a space
("Recurring , 3 waiting"); the end-to-end regexes that tolerated the space are exact now.
Cost if wrong: none.

### R17: Saving from the last occurrence starts the schedule after it, and the offered date is an entry within the end date

What was ruled: three decisions the R10 fix left open. (a) When the date an edit saves from is the due day of the rule's last
occurrence (which is where the form anchors a rule that ran out), the next due day is looked for AFTER that day, not from it,
by one function, `datesFromAnchor` (`src/domain/recurrence.ts`), which `editRule`, the "too many due now" check in `prepare`
and the form's preview (`entriesDueNow`, `nextDatesPreview`) all use, so the preview says exactly what a save makes. The entry
on that day is already counted in the rule's occurrences, and counting it again as a date of the new grid spent the occurrence
limit on it twice (raising a spent limit of 3 to 5 made one more entry, not two), listed the day under "Next dates", said an
entry would be posted now when none was, and counted it towards the 100 that may fall due at once. The generator's own
conflict skip alone does not cover that: the count is taken before it, and the preview never ran it. The form is given the day
through `editing.lastDueOn`.
(b) The date offered is the latest entry ON OR BEFORE the rule's end date (`findLastDueOn(userId, ruleId, onOrBefore)`, which
`loadRuleForEdit` and `editRule` call with the stored end date). A rule whose end date was edited to before its last entry
(the edit form allows an earlier next due day, so it is reachable) would otherwise be offered its end date, which is not an
entry it has when it is off the dates it has, and a rename would make an entry there (and a transaction with automatic
posting). With a bound the save is always from an entry that exists. `editRule` uses the STORED end date, as the form did, so
the answer is the same when the person also changes the end date in the same save.
(c) Only when the rule has no entry on or before its end date at all (they are all after it) is the offered date held to the
end date (`anchorOfRunOutRule`), which a save would otherwise refuse to start after; an end date off the rule's dates can then
propose itself, in that one case, which the person chose by setting both dates.
Cost if wrong: `datesFromAnchor`, the `lastDueOn` arguments in `editRule` and `loadRuleForEdit`, and `anchorOfRunOutRule`.

## Known and parked

Found in review and left alone on purpose. None of it puts money or another user's data at risk. The final review's blocking and should-fix findings (the pending count on every page, a late replay of a create, a stale card's post, the month-end draft, deleting an account a rule names, a failing rule aborting the rest, and the smaller items beside them) were fixed in a last wave and are no longer listed. Grouped by where it is.

**History and the ledger**
- Deleting the transaction behind a posted entry leaves the entry posted (EC-45): it is history, and the Recently handled row still shows what was recorded.
- A crash between committing the generated entries and auto-posting leaves an auto-post entry silently pending, with no "not posted automatically" note; nothing retries it, the money is safe and the entry is in the inbox.

**Sweep timer**
- No guard against a second `register()` call (two timers), and `stop()` is not wired to shutdown; `intervalMs` against the environment's precedence and `unref` are untested; a throwing injected logger would leave an unhandled rejection (theoretical).
- The programmatic `intervalMs` option is not bounded by the 2147483647 ceiling (only the environment path is), and the README does not state the ceiling.

**Schedule arithmetic (`src/domain/recurrence.ts`)**
- `datesDue` accepts an interval of 1.5 or Infinity (should be `Number.isInteger`), and a day of month of 0 or less throws from `calendarDate` instead of returning no dates; its defensive `??` defaults repeat `normaliseSchedule` and need a comment; a few lines run past 120 characters.

**Schema and repository**
- The due-scan index `(userId, nextDueOn)` does not serve the global sweep query `findUsersWithRulesDueBy`; the table is tiny at personal scale, and `(nextDueOn)` can be added if it ever matters.
- The migration comment says "like every other FK" though `parentId` and `groupId` are `SET NULL`; no test asserts that the `RecurringRule` `updated_at` trigger fires.
- `mark*` and `insertOccurrences` do not themselves require a live rule (the service closes that, see R6); `markPosted` accepts a soft-deleted transaction; `findUsersWithRulesDueBy` uses `distinct` where `groupBy` would push the dedupe into SQL; `findOccurrenceById` and `findRecentlyHandled` do not scope the rule join by user (safe, since occurrences are only inserted for the user's own rules); `findRecentlyHandled` accepts an unbounded or non-finite limit; the duplicate-key lookup runs inside an uncommitted unit of work.
- Two repository isolation cases depend on file order, and the concurrent-insert test is probabilistic.

**Occurrence and rule services**
- The QUANTITY predicate is written twice (`recurring-view.ts` and `lotModeOf`) with no parity test; the soft-deleted-transaction fallback by idempotency key and the paused-or-deleted re-checks after the lock have no direct test.
- A sweep that moves `nextDueOn` bumps the rule's version, so an edit form open at that moment meets a conflict and reloads (accepted, safe).
- `editRule` validates an archived end strictly, so a blocked rule cannot be renamed, and a blocked daily rule more than 100 days behind cannot be edited at all (the too-many-due check still applies to it, since saving a fix un-blocks it and it would generate at once; see R10); `createRule` throws if reading today or the due rules fails after the insert (a single rule's failure no longer does, see R15) where it could fall back to the stored rule; the `setPaused` retry path is untested and wants a comment; one comment (`anchorField`) is stale.
- Post sends the card's amount and note but not its tags (the post schema has no tags override), so tags edited on the rule since the card was drawn are the ones recorded (R11).

**Actions and loaders**
- The investments and nodes actions still carry their own copies of `parseInput` and `violationFieldErrors`; the result-shape check for bigint leaks covers success results only, not conflicts and field errors; `loadRecurringScreen` reads without a snapshot, so a node created mid-read could throw (negligible); the archived-end and lot-purchase cases of `templateFromTransaction` are untested; there is no loader test for the posted branch of `recent` or for a mix of live and deleted rules.

**Inbox and rules screen**
- Post on a quantity entry while its form is open does nothing, though `aria-expanded` suggests a toggle; Pause, Resume and Delete drop keyboard focus while pending (`aria-disabled` would keep it) and lack the in-flight guard the cards have; the reason an archived entry cannot be posted is visible text only, and disabled buttons are skipped by Tab.
- `putBack` is imported from `recent-list.tsx` (it belongs in `feedback.ts`) and `inbox-card.tsx` is about 400 lines; an animation-frame focus is not cancelled on unmount; one test reads the source with a regular expression; there is no interaction test for the quantity focus; the narrow-screen case of a long amount beside a long name was checked at desktop width only.

**Proof and process (accepted by the final review)**
- The end-to-end isolation proof for `findPending` is defence-in-depth: with both of its filters removed it fails only through a crash on `/recurring`, not through a leak assertion. The direct proof is the repository isolation tests.
- The `countPending` and `findRecentlyHandled` user filters were not mutation-tested: no test was shown to fail with one of them removed.
- A user-chosen transaction idempotency key of the form `recurring:<id of their own pending occurrence>` can pre-empt that occurrence's post, since posting reuses the key. It concerns only the user's own data.
- Several app replicas would each run a sweep. The per-rule row lock and the `ON CONFLICT DO NOTHING` occurrence insert make that safe (nothing is proposed twice); it is only wasted work.

**End-to-end specs**
- A few `toBeVisible` assertions add little; `getByRole("status")` and some named forms are not scoped to the visible `main`; the `PASSWORD` constant repeats the one in the fixtures.

**Rule form**
- The submit logic (request-key reuse, `expectedVersion`, the conflict branch, the payload shape, the redirect) has no unit test of its own; the end-to-end suite covers creating, not conflicts.
- A stale "Reloaded" flash can persist in session storage if the reload 404s; the automatic-posting helper text is not tied to its control by `aria-describedby` (the reason id is unused); `startOpen` is a test-only prop on the production `EntryRow`; small nits (a `maxLength` of 500 repeating `NOTE_MAX_LENGTH`, a `CalendarDate` cast, a test asserting a class name, a misnamed render test, a Fragment's indentation).

## What M4 does not do

The design's non-goals, recorded so a later request is not read as a regression.

- **No bulk actions.** There is no "post all"; every entry is posted, changed or skipped on its own card.
- **No calendar view.** The inbox is a list, oldest first, and the rules are a list.
- **No split templates, and no EMI.** A rule is one two-sided transaction; a loan payment split into principal and interest is not a rule (`GroupKind.EMI` stays unused).
- **No notifications.** No email and no push; the inbox, the navigation badge and the dashboard notice are the notification.
- **No forecasts.** No projected balance, and a pending entry is counted in no figure: not a balance, not net worth, not a report.
- **No "from rule" chip** on the Transactions list. The link from a posted entry to its rule exists in the table; showing it is a later request.
- **No RRULE strings or irregular schedules.** The structured schedule is the decision; RRULE is the upgrade path.
- **No budgets and no CSV import**, and so no matching of imports to pending entries (M5 and M6).
