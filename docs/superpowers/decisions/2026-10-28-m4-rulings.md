### R1: The sweep timer runs under `bun --bun run start`, so the cron fallback is not needed

What was run: design §11 names the production runtime as the risk to settle first, because the container starts the
app with `bun --bun run start`. `src/instrumentation.ts` exports `register()`, which (on `NEXT_RUNTIME === "nodejs"`)
starts `startSweepTimer` from `src/server/sweep-timer.ts` with a stub run function that logs `[recurring-sweep] tick`.
After `bun run build`, on the host against the dev database (the stub does not touch it), port 3301:

```
$ RECURRING_SWEEP_INTERVAL_MS=2000 bun --bun run start -p 3301     # killed after about 7 seconds
$ next start -p "3301"
▲ Next.js 16.1.3
✓ Starting...
[recurring-sweep] tick
✓ Ready in 193ms
[recurring-sweep] tick
[recurring-sweep] tick
[recurring-sweep] tick

$ RECURRING_SWEEP=off RECURRING_SWEEP_INTERVAL_MS=2000 bun --bun run start -p 3301     # same 7 seconds
$ next start -p "3301"
▲ Next.js 16.1.3
✓ Starting...
✓ Ready in 133ms
```

Versions: Bun 1.4.3 (the Dockerfile's `oven/bun:1.4.3` pin), Next.js 16.1.3.

Outcome: `register()` ran, the first tick fired at startup (before "Ready"), and two more fired at the 2 s interval; the
timer stayed alive for the whole run despite being `unref`'d (the HTTP server keeps the process up). With
`RECURRING_SWEEP=off` there were no ticks. The in-process timer is therefore the mechanism. The `POST` route fallback
(design §11) was not built.
Caveat: this ran on the host with Bun as the runtime, not inside the Docker image; the image uses the same Bun version and
start command, and `NEXT_RUNTIME` is `nodejs` under `next start` in both.
Cost if wrong: one secret-guarded route and a README line (the design's fallback), nothing else changes.
