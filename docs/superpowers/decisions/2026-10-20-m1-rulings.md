# AccuFi M1 — decisions taken during implementation

Every ruling made while executing `docs/superpowers/plans/2026-10-20-accufi-m0-m1-foundation.md`,
in the order it was made. Each was a decision taken on the commissioner's behalf because the spec
was silent, self-contradictory, or wrong. Each records what it costs if it turns out to be wrong.

Four of these reverse an earlier decision of my own; those are marked. Three spec amendments
followed from them and are committed separately (6db9f90, 4ddc9f2, 3b9bd35).

The independent whole-branch review audited all of these and judged none of them wrong.

---

## Pre-flight rulings (made before any code was written)

These came from a conflict scan across the plan's 14 tasks, before Task 1 was dispatched.

### R1

T6's `core_ledger` migration drops the `HealthCheck` model and table; the health route switches to a plain `SELECT 1` with no model dependency — a liveness probe should not need a table. Cost if wrong: a dead table lingers, droppable in one migration.
### R2

`sumBalances(userId: string, asOf?: CalendarDate)` — `asOf` optional, undefined meaning no upper bound. Spec EC-10 requires both the current and the projected figure, so both callers are legitimate. Cost if wrong: none; the required-arg form is strictly less capable.
### R3

`src/domain/ledger-kind.ts` is canonical. T6 adds a test asserting the Prisma-generated `LedgerKind` and `SystemNodeRole` enum values equal the domain's exactly, in both directions. The Global Constraint forbids the domain importing Prisma, so a shared type is impossible and a pinning test is the available guarantee. Cost if wrong: none; it is an extra test.
### R4

`sumBalances` is rewritten to `LEFT JOIN` from `LedgerNode`, returning one row per non-archived node with its `kind` and `COALESCE(sum, 0)`. The plan's GROUP BY-over-transactions SQL cannot satisfy its own zero-balance test or populate `NodeBalance.kind`. Cost if wrong: zero-balance accounts vanish from the dashboard — visible on first run.
### R5

`createLedgerNode` writes its opening-balance transaction through `transaction-repository.insertTransactions`, not through `transaction-service` (which does not exist until T11). The flow `INCOME_SOURCE → ASSET`/`LIABILITY` is legal by spec §5 regardless, so no service-level validation is bypassed. Cost if wrong: a small refactor to route it through the service later.
### R6

T10's node list reads balances via `sumBalances` from the repository directly; T14's `balance-service` wraps the same call for the dashboard. Cost if wrong: minor duplication, collapsible into the service.
### R7

split legs get per-leg idempotency keys of the form `<key>:<index>`, preserving the `@@unique([userId, idempotencyKey])` constraint from T6 unchanged. All legs are written in one DB transaction, so a replay either finds every leg present or none. Cost if wrong: a retried split whose leg order changed could double-post; mitigated by the single-transaction write.

## Rulings made during execution

### Task 1

fix round 1 carries Important #1 plus Minors 1, 2, 3, 4 and the .env.example half of Minor 8, deviating from the default that Minors never enter the loop. Why: Minors 1 and 2 are holes in this task's own deliverable (the purity lint rules), and Tasks 2-5 write exactly the domain and money code those rules exist to police — a rule with holes gives false assurance at the moment it matters most. Minor 4 protects the spike conclusion that 13 tasks rest on, which the probe showed depends on an image symlink. Minor 3 is one line against a swallowed error. Cost if wrong: one extra fix round on a task that was already entering the loop.
### Task 1

Minors 5 (container runs as root, dev deps in runner), 6 (no BigInt round-trip under the container runtime) and 7 (prisma generate not wired to postinstall) are deferred, not fixed. Minor 6 is already covered by Task 6's planned BigInt round-trip test; Minor 7 cannot bite this session because the checkout is shared and already generated; Minor 5 is deployment hardening with no v1 deployment. Cost if wrong: a fresh clone needs one manual `prisma generate`, and the container stays root until hardening.
### Task 2

accept the out-of-brief tsconfig `target` bump ES2017→ES2020. BigInt literals are a TS2737 error below ES2020, so the plan's integer-paise constraint is unimplementable at the old target; the plan simply missed this prerequisite. noEmit + SWC means no runtime effect. Cost if wrong: none identified; ES2020 is well within Next 16 / Bun 1.4 support.
### Task 2

Minor 1 (deserialisePaise throws RangeError while parseRupees throws MoneyParseError) is NOT deferred; it is folded into Task 3's dispatch as a scoped prerequisite. Reason: it is an interface contract eight later tasks consume, nothing consumes it yet so the fix is free today, and a boundary handler catching only MoneyParseError would turn a malformed form field into a 500. Routing it through Task 3 rather than a Task 2 fix round keeps minors out of the loop while still landing the fix immediately, and it gets reviewed as part of Task 3. Cost if wrong: one unrelated line inside Task 3's diff.
### Task 3

Vitest does not resolve the `@/*` tsconfig alias, so src/lib had to import the domain by relative path. This is infrastructure every task from 6 onward will hit, because their tests import src/server modules that use `@/`. Folding a one-line vitest.config.ts alias into Task 4's dispatch as a prerequisite rather than leaving each later implementer to rediscover it mid-task. Cost if wrong: one config line inside Task 4's diff.
### Task 6

the four enum member sets the implementer inferred are CORRECT. Verified each against the spec myself: AssetSubtype SAVINGS/CURRENT/CASH/WALLET (§8.1 line 261), LiabilitySubtype CREDIT_CARD/LOAN (line 262), ValuationMode QUANTITY/LUMP/CONTRIBUTION_ONLY (§7.1), LotMethod FIFO/LIFO/HIGHEST_COST_FIRST (§7.5 "FIFO by default, configurable per node to LIFO or highest-cost-first"). Cost if wrong: none; they match the spec text verbatim.
### Task 6

fix round 1 carries the Important enum-parity gap plus three items the reviewer rated Minor or raised as a ⚠️. (a) No `typecheck` script exists anywhere, so `tsc --noEmit` is never run by `bun run test` — that is the hole that lets the Important finding hide, and it silently weakens every task's type safety, not just this one. (b) EC-66's updatedAt gap: a BEFORE UPDATE trigger is ~5 lines and fully closes a constraint the spec states unconditionally; the reviewer itself says to settle it before the edit-transaction task. (c) The test-DB name guard matches the substring "test", so a database named `contest` would pass it — a one-character regex fix protecting the dev database from a stray write. Cost if wrong: one extra fix round on a task already entering the loop.
### Task 6

deferring Minor 2 (domain-only test runs require Postgres + bunx via globalSetup). It is a DX wrinkle on a solo project where Docker is always up, and the clean fix is a vitest workspace split that is disproportionate right now. Cost if wrong: slower inner loop for domain-only work.
### Task 7

(pre-dispatch) — the plan specifies Auth.js v5 "with the Prisma adapter; database sessions" AND a Credentials provider. Auth.js does not support database sessions with Credentials; it forces the JWT strategy. The plan asserted an unavailable combination. Resolution: keep the Prisma adapter for user persistence and use the JWT session strategy, with an httpOnly, secure, sameSite cookie. Nothing in the spec depends on server-side session revocation. Cost if wrong: sessions cannot be revoked server-side before expiry; mitigated by a short maxAge, and migrating to DB sessions later would need a different provider shape anyway.
### Task 7

CORRECTING my own pre-dispatch ruling. I said "keep the Prisma adapter for user persistence"; the implementer did not add it and was right not to. With Credentials + JWT, Auth.js never invokes the adapter, so it would be dead code that adds empty Account/Session tables and unused User columns. The implementer disclosed the departure plainly instead of silently complying or silently deviating. Accepted. Cost if wrong: adding the adapter later is a migration plus a config line.
### Task 7

accepting the known JWT consequence: a deleted or disabled user's session stays valid until expiry (<=24h) because requireUserId does not hit the DB. Cross-user leakage is not possible (writes fail on the FK, and every query is userId-scoped), so the exposure is bounded to a stale self-session. Cost if wrong: no server-side revocation until the session expires; a DB lookup in requireUserId would close it at the price of a query per action.
### Task 7

on plan-mandated signup enumeration (Important 3): KEEP the explicit EmailTakenError message. For a self-hosted tracker with no email delivery there is no "we sent you a link" dodge, so hiding it costs real UX for little gain. But the implementer's claimed mitigation is wrong — the limiter keys on (ip,email), so every probed address starts with a full budget and bulk enumeration is unimpeded. Require a coarse IP-or-global signup counter instead. Cost if wrong: account existence stays discoverable at a bounded rate on a self-hosted deployment.
### Task 7

folding five Minors into the fix round alongside the three Importants: explicit argon2 cost parameters (a ^2.2.2 upgrade could otherwise silently change the work factor); a route-guard test pinning config.matcher and the handler's redirect (today nothing would catch a matcher edit that silently unguards routes — the same false-assurance class as Task 6's enum test); the Session type declaring id as a non-optional string while the callback assigns it conditionally; AUTH_URL fail-fast in production (trustHost:true plus an empty AUTH_URL falls back to the Host header for redirects); and dropping the unnecessary windowStart default. All cheap, all security-adjacent, all on a task already in the loop.
### Task 8

carrying three items from Task 7's re-review into Task 8's dispatch as prerequisites rather than deferring them. (a) A ~0.4%-per-run flaky test: two signup tests draw a random last octet from the same 250-value space and share a key that excludes the email, so a collision makes one see an exhausted budget. A flaky test in a suite seven more tasks must trust will send some future implementer chasing a ghost. (b) The lockout documentation says 30 where the shipped default is 10. (c) `eslint` covers only src/, so tests/ — now a large fraction of the codebase — is unlinted, which is how a duplicate vitest import survived. Cost if wrong: three small unrelated changes inside Task 8's diff.
### Task 8

fix round 1 carries both Importants plus five Minors: the meta-test that the report described as enforcement but which only compares a derived list to a hand-maintained one (a developer satisfies it by adding a string, writing no test — the same false-assurance class as Task 6's enum test and Task 7's matcher test); a page-size assertion that cannot fail against its 4-row fixture; two comments that are provably untrue as committed (node-repository claiming sole ownership of LedgerNode writes while account-seed writes them directly, and countTransactionsForNode's doc over-claiming); the missing id tie-break on the keyset index; and the Prisma deprecation warning. Cost if wrong: one extra round on a task already in the loop.
### Task 9

MAJOR, and the implementer found a defect in MY SPEC, not in anyone's code. sumBalances returns inflows−outflows uniformly, so a card you owe ₹5,000 on has balance -500000n; netWorth accumulated liabilities as a positive magnitude and SUBTRACTED, giving total = assets − (−500000). Spending on a credit card increased net worth. Task 5's unit tests passed only because they hand-feed a positive liability balance that sumBalances will never produce — the two layers had never been wired together. Spec line 80 ("Yes, as a negative") and line 116 ("− Σ LIABILITY balances") asserted both conventions at once. Resolution, now written into the spec: sumBalances is the single source of truth and is unchanged; netWorth adds the already-negative balances and reports NetWorth.liabilities as the positive magnitude for display. Required a cross-boundary integration test, since the gap existed exactly because no test crossed it. Cost if wrong: the headline figure on the dashboard is wrong in the direction that flatters the user.
### Task 9

adding system node OPENING_BALANCE_CONTRA (kind EXPENSE). The implementer showed "I already owe X" cannot be posted as an opening balance: OPENING_BALANCE is an INCOME_SOURCE, INCOME_SOURCE → LIABILITY makes the balance positive (paying debt down), and INCOME_SOURCE can never be a target — so no legal edge makes a balance negative at setup. Positive opening positions post OPENING_BALANCE → node; negative ones post node → OPENING_BALANCE_CONTRA, implemented by sign rather than by kind so it also covers an overdrawn asset account. Needs a SYSTEM_NODE_ROLES member, a Prisma enum value, an additive migration and seeding. Cost if wrong: an extra system node per user and one enum value; the alternative designs all required special-casing a node out of net worth.
### Task 9

also requiring, pre-review: one $transaction around node creation + opening-balance posting (today's compensating delete leaves an orphan on a crash between the two writes), and an explicit runtime kind-immutability refusal in the service rather than relying on structure plus a strict schema.
### Task 9

CORRECTING my own ruling R4. I told Task 8 that sumBalances should return "one row per NON-ARCHIVED node". EC-32 requires an archived node's balance to remain in net worth, so as built, archiving a credit card with ₹50,000 owed silently RAISES net worth by ₹50,000 — the same family of defect as the liability-sign bug this task just fixed, and found in the same review. Resolution: sumBalances includes archived nodes; NodeBalance carries an `archived` flag so display-only filtering (pickers, the account list) stays a caller concern. Spec EC-32 updated to say so explicitly. Cost if wrong: the dashboard's account list must filter archived rows itself, which it already does via findNodes.
### Task 9

the unit-of-work callback must hand services an OPAQUE token, not a raw Prisma.TransactionClient. Today a service could write `tx.ledgerNode.findMany({})` with no userId and no Prisma import, so the grep that normally reveals a boundary violation would miss it, and no ESLint rule covers src/server/services. Declaring UnitOfWork as a branded opaque type that repositories cast internally makes the misuse a compile error rather than a convention. Cost if wrong: one cast inside each repository entry point.
### Task 11

Important 2 is plan-mandated and my brief was wrong, not the implementer. The brief said "allowArchived: true on an edit" without qualification; its stated reason was only that a historical row referencing an already-archived node stays correctable. Spec EC-14 is already precise ("Archived nodes never appear in pickers for NEW entries"), so the brief over-generalised the spec. Resolution: keep allowArchived: true, then additionally reject any node id the edit NEWLY introduces that is archived. Cost if wrong: a crafted payload could still point a live transaction at a node the user has retired.
### Task 11

settling the blockNegative policy now, before Task 13/14 makes the flag settable: deletion is NEVER blocked by the overdraft guard. A user must always be able to remove a mistaken entry; blocking deletion strands the error with no way out. Edit and restore stay guarded. The policy goes in the module header in one place rather than being inferred from four call sites. Cost if wrong: a determined user can route around the guard by deleting and re-entering, which is a UX speed bump rather than a control.
### Task 13

on the Important finding, FIX THE PRODUCT, not the spec. Hiding system nodes from the pickers, combined with openingBalance existing only on the node CREATE schema with no update action, makes spec EC-36 ("Setting an opening balance after transactions exist — Allowed") unreachable: a user who forgets an opening balance has no supported way to add one short of destroying and recreating the account, losing its history. Forgetting an opening balance is one of the most common real-world setup mistakes, so the capability is worth keeping. Offer the two opening-balance system nodes as SOURCES only, in their own optgroup, which satisfies EC-36 without making them easy to mispick. Cost if wrong: two extra entries in one picker.
### Task 13

CORRECTING my own EC-36 fix instruction. I wrote "offer the two opening-balance system nodes as SOURCES only" and asked for a test proving the contra node can never be a destination. That is incoherent: the two nodes are mirror images, not a pair. OPENING_BALANCE is an INCOME_SOURCE and is source-only (the flow matrix already forbids it as a target, so no picker rule is even needed). OPENING_BALANCE_CONTRA is an EXPENSE and exists precisely to BE a destination — a negative opening position posts account → Contra. My instruction made the node unreachable in the only direction it serves, so a forgotten POSITIVE opening balance became recordable while a forgotten NEGATIVE one (an owed card, an overdrawn account) stayed impossible. Corrected: OPENING_BALANCE source-only, OPENING_BALANCE_CONTRA destination-only, both in the Setup group; Realised Gain and Loss hidden in both directions until the milestone that owns disposals. The test I asked for is inverted, and the four system roles × two directions are now pinned as one table-driven test so a later milestone cannot quietly widen it. Cost if wrong: two picker entries.
