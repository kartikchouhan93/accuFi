# AccuFi M6 — CSV import Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A user uploads a bank or card statement CSV for one account, maps its columns with explicit choices, reviews each row (counterpart ledger, probable duplicates, matching recurring entries), and commits everything in one transaction, with every imported transaction traceable to its batch and the whole batch reversible.

**Architecture:** Pure domain modules tokenize, parse and match (CSV text to rows, explicit date and amount formats, duplicate and recurring-occurrence matching, learned-rule suggestions). Four new tables (`ImportBatch`, `ImportRow`, `ImportProfile`, `CounterpartRule`) and two nullable columns on `Transaction`. A service stages rows, edits decisions under conditional updates, and commits or reverses under a batch row lock. Screens are server-rendered wizard pages; the upload goes through a route handler that enforces the size cap.

**Tech Stack:** Bun, Next.js 16 App Router (Server Components, Server Actions, one route handler), React 19, Prisma 6 / PostgreSQL, Zod 4, Tailwind 4, Vitest, Playwright. No new dependency (hand-written tokenizer, `TextDecoder`, `node:crypto`).

**Spec:** `docs/superpowers/specs/2026-11-02-accufi-m6-csv-import-design.md` (parent: `2026-09-11-accufi-design.md` §8.6, EC-17, EC-46, EC-53 to EC-60).

## Global Constraints

- Money is integer paise (`bigint`, `Paise`), never `number`; text across the server/client boundary. Parsing never rounds: more than two decimals, zero, or unparseable is a row error. Dates are `CalendarDate`; both timezone passes (`sh scripts/test-tz.sh`) stay green; tests never depend on the real date.
- Layering: `src/domain` pure (no Prisma, Next or server imports; value imports of other domain/lib code are **relative**); repositories take `userId` first and put it in every query and join; services orchestrate; `src/app/**` Server Components pass plain props and never write during render.
- Direction is relative to the batch's account: **OUT** = `account → counterpart` (money leaves a bank account, or a charge increases what a card owes), **IN** = `counterpart → account`. Single signed column: the user picks `POSITIVE_OUT` or `POSITIVE_IN` explicitly; debit column = OUT, credit column = IN; a trailing `Dr`/`Cr` overrides the convention for that row. A date format is **never inferred** (EC-53); delimiter and encoding are chosen, never guessed.
- Date formats (closed list): `DD/MM/YYYY`, `MM/DD/YYYY`, `YYYY-MM-DD`, `DD-MM-YYYY`, `DD/MM/YY`, `MM/DD/YY`, `DD-MMM-YYYY`, `D MMM YYYY`; two-digit years mean 20yy; impossible dates (`31/02/2026`) are errors.
- Limits: `IMPORT_MAX_BYTES = 5 * 1024 * 1024`, `IMPORT_MAX_ROWS = 20_000`; a file with NUL bytes (and no UTF-16 BOM) is refused as not text. Upload enforced server-side (route handler checks `content-length` and the real size).
- Duplicates (EC-55): a live transaction touching the account, same amount, same direction relative to the account, date within `DUPLICATE_WINDOW_DAYS = 3` either side; imported or typed makes no difference; **never** flagged within the same file; flagged rows are decided, never dropped. A pending recurring occurrence (EC-46) of a live rule touching the account with the same amount and direction, due within 3 days, may be linked; linking records the **bank's** date and amount and takes the counterpart from the rule.
- Nothing is committed until the last stage; commit is one database transaction under `FOR UPDATE` on the batch, requires status `STAGED` (a repeat returns the first result), and is idempotent per row through key `import:<rowId>` (always at least 16 characters). A commit that fails writes nothing and leaves the batch `STAGED`. Reversal soft-deletes exactly the batch's transactions and returns occurrences they had posted to `PENDING`.
- A transaction made by import is held to the same rules as any other: `validateTransaction`, archived ledgers refused, no investment held by lots as counterpart, the overdraft guard for `blockNegative` ledgers (applied to the batch as a whole at commit; reversal is **not** guarded).
- Statement text is the user's most sensitive data: raw bytes are stored only while the batch is `UPLOADED` or `STAGED` and are deleted when it is committed, discarded or reversed; file content is never logged and never appears in an error message.
- Deleting a ledger an import batch names is refused with a message, not a foreign-key crash; its profiles and learned rules are removed with it.
- Cross-user isolation per repository method (the coverage test in `tests/server/repositories/isolation.test.ts` enumerates repository exports); the isolation e2e covers `/import`.
- Lessons already paid for: `bunx prisma migrate deploy` (not `migrate dev`), remove generated no-op `SET DEFAULT now()` statements, `updatedAt` trigger convention (EC-66); pool caps 4 per vitest worker and 10 per e2e process; wrap every count read shown on every page (try/catch to 0, `cache()`); pin every message wording with a test; e2e lookups use explicit `from`/`to`, scope locators to the visible `main`; names carry an sr-only suffix; `aria-disabled` rather than `disabled` where focus would be lost.
- Palette: Graphite & Azure tokens only (no purple, no yellow), light and dark, keyboard reachable, visible focus, reduced motion, no horizontal scroll at 375px (wide tables scroll inside a labelled focusable frame). Status never by colour alone.
- Every commit message ends with `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>`.
- Test commands: a file in both zones `sh scripts/test-tz.sh <path>` (prefix `PATH=$PWD/node_modules/.bin:$PATH` if vitest is not found); everything `bun run test`; `bun run lint`; e2e `bunx playwright test <path>`.

## Review Focus

Inputs the spec implies that no obvious test reaches; each has a test in the task named.

1. Ambiguous and impossible dates and amounts: `03/04/2026` both ways, `31/02/2026`, a leap day, Indian grouping, a third decimal, zero, text, a `0.00` in the unused debit/credit column. (Tasks 1, 2)
2. A commit that fails on the third row, two tabs committing at once, a double click: nothing partial, no duplicates, the batch still reviewable. (Task 8)
3. A ledger archived, a flow that stopped being legal, or a recurring entry handled between staging and commit: the whole commit refuses and names the rows. (Tasks 7, 8)
4. An identical file uploaded again (warns), an overlapping statement (duplicates flagged, none dropped), a discarded earlier upload (does not warn). (Tasks 3, 6)
5. Reversal: balances return to exact earlier values, only the batch's transactions go, a hand-entered transaction in the same period survives, a linked recurring entry returns to the inbox, a second reversal is safe. (Task 8)
